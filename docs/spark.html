How Meta Muse Spark runs Shiptorio

Shiptorio turns a GitHub repo into a factory game, and every PR it ships is real. One model, Meta Muse Spark (muse-spark-1.3 on the Meta Model API), is the brain. It sorts the work, plans every job, reviews every PR, judges what happens after launch, and decides which card the player sees next. The player's Claude Code or Codex subscription only builds what Spark planned. Spark never writes code, and it can never merge past a failed check.

A real run: PR #87

The first factory-built PR on Shiptorio's own repo. Issue #71 asked to block direnv credential files from the assembler's path guard. Here is what happened, taken from the PR record.

1
The issue came in from GitHub as ore. The player approved the job and its two-file scope: server/src/engine.ts and server/test/engine.test.ts.
2
Spark planned it in its read-only tool loop (read_issue → read_file → assign_job). The plan it handed the builder:
“Extend the existing dotenv basename guard … to also block the direnv basename, case-insensitively, at any depth … Keep the public SAFE_PATH test interface unchanged … change no other files, dependencies, or CI deployment configuration.”
Acceptance: direnv names refused at any depth · lookalike files still accepted · only the two approved files modified.
3
Codex built it on Justin's Mac through the local runner. The supervisor checked the scope, ran a secret scan, then ran typecheck, tests and build.
4
The verify bay proved it with real execution. The new test fails on base (exit 1) and passes on head (11 pass, 0 fail).
5
Justin merged it. That run exposed the review-comment gap that #149 fixes. A merge that lands before AI review finishes is now logged as such, and a failed review comment retries out loud.

Why the split

Spark proposes, rules dispose

Spark can reorder cards and suggest options, but it can't invent an action, skip a station or grant a permit. Automation is earned by clean ships, and the proof that earns it stays deterministic.

Untrusted inputs

Issue text, diffs, Sentry errors and scars all go to Spark as evidence, never as instructions. Every prompt says so, and every reply is parsed against a fixed set of allowed ids.

Nothing hidden

Every Spark call lands in the in-game "How it thinks" log: what it looked at, what it decided, why, and how long it took. Every time a rule had to stand in, that's counted too.

Is it any good? The scorecard

Counting calls only shows Spark is busy. The scorecard in "How it thinks" shows whether its calls hold up, measured from what really happened on GitHub.

Plans shipped

Of the jobs Spark planned, how many merged and launched. A re-plan after a failed check is the same job, so retries can't pad it. Jobs still on the line count as not shipped yet.

Reviews that caught a problem

Of the PRs Spark reviewed, how many it sent back for rework. Zero would mean it rubber-stamps; the rework belt shows what each catch was.

Calls a rule had to make

The share of decisions where Spark didn't answer and a fixed rule stood in. Lower is better, and it's never hidden.

Check it yourself

On GitHub: each planned issue gets a comment with Spark's triage reason, each tool call and the plan. Each reviewed PR gets a “Muse Spark reviewing X's work” comment.

In the game: open the bell menu, then powered by Meta Muse Spark · how it thinks.

In the code: server/src/spark.ts (every prompt), server/src/brain.ts (the decision log), docs/context/spark-audit.md (the audit). bun run spark:check runs every prompt against the live API.
